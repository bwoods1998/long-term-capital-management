# Developmental program cards

A survivor can have a repaired program whose implemented mechanism differs from its birth card. Replacing the immutable family card would rewrite the terms of its historical evidence. Merely running the repaired source under that card can also carry over the legacy hypothesis's broad-replay exemption.

`gym_run` accepts an optional `development_card` with exactly `card`, `parent_version`, `parent_sha`, and `parent_params`. The card passes the ordinary controlled vocabulary/completeness checks. The parent must be the family's actual latest version, its source bytes must hash to the declared source identity, and the run carries exactly that parent's stored overrides. The submitted code must be new to the same family. This is a developmental proposal, not an empirical finding or a new family.

Admission requires explicit `researcher.development_cards: true` and the ordinary mechanism test enabled in `gate` mode. The setting defaults to false. Existing gate, unseen, extension and pending-Validation holds refuse registration. Static experiment checks and preflight still precede registration. Parent and hold checks repeat inside the normal registration transaction, before roots or versions change. The normal `gym_run` handler registers the version; there is no alternative registration endpoint.

The append-only `development_cards` table binds the same family/lineage, exact code SHA and overrides, actual parent, structure, and canonical card. Its SHA hashes that complete binding; `card_content_sha` separately hashes the card text. Updates/deletes are refused. `family_cards`, historical versions/evidence, inherited trials, looks, failed versions, and holds remain. Existing source cannot be recarded to transfer qualification. Once a family enrolls, new source or different overrides require a new declaration; a sweep refuses because it does not declare a card per exact variant. An exact retry selects the saved developmental card automatically, with its original parent retained.

A developmental card has no legacy broad-replay exemption. Earlier broad Train exposure remains recorded separately as `exposed`; it never becomes a fresh blind or unfitted test merely because the card changed. Only its own binding's recorded mechanism pass opens broad Train. Connected-lineage failed evidence, including explicit failed version metadata retained in family state, still raises the ordinary noise bound; historical own failures below the base bound still count toward mechanism retirement. Unknown/redacted historical verdicts remain unknown. The mechanism test identity includes the binding SHA. The standard ablation, staged jobs, profile audit, thin/invalid/failure refusals, per-arm trial accounting, and subsequent Train/robustness/drift/Validation/unseen requirements remain. A mechanism pass follows the ordinary behavior of skipping the zero-trade probe because that sample already traded; other normal admissions still exercise the usual probe.

The card states a hypothesis and an estimated cost hurdle. Neither is measured evidence. Causal-comparison source changes need review: the off arm must preserve direction, structure, tenor, strikes, sizing, cadence and exits while bypassing only the declared condition. A new label or source comment cannot qualify a program.

`league.tests.test_swarm_development_cards` uses a fabricated Gym and temporary stores. It tests actual parent bytes, explicit enablement, holds and concurrent changes, immutable exact retries, lineage failures/N, ordinary probe/refusal behavior, and a purely invented pass reaching broad replay. No fixture proves market profit, market qualification, native model admission, budget authority, deployed rollback readiness or exact-new-head CI.

Before actual adoption, the owner of the research harness must review the source/card/comparison, bind the permitted clean data and evaluator, complete exact-head CI and native isolation/budget checks, and use these normal admission arguments. The software is prepared without actual registration or any financial activation. For a rollback after enrollment, stop research rather than running a release that ignores developmental cards; retain every new trial/evidence row and resume only with a compatible card-aware release. This document does not certify that rollback rehearsal.
